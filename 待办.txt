【5】暂时未实现 MDM Agent 的批量更新
  位置：平台基础管理 · MDM 版本 Tab（前端操作入口）；相关表 t_mdm_app_version；包名配置 MDM_AGENT_BUNDLE_NAME
  现状：版本仓库、上传 HAP、发布，以及端侧 GET /api/mdm/getInfo 已打通；
        管理台「按分组/设备批量推送 MDM Agent 升级」尚未实现。
  后续：在 MDM 版本管理页增加「批量下发」能力（目标选择、任务记录、MQTT 通知、进度等）。
  说明：与普通「应用管理」的批量安装/卸载区分——此处专指 MDM Agent 自身升级。

  实现思路（草案，待端云对齐后落地）：
  1. 前端：平台基础管理 → MDM 版本 Tab，对已发布版本增加「批量下发」入口
     （选设备 / 按分组，发起升级通知任务；与应用仓库批量安装入口分离）。
  2. MQTT：云 → 端发一条「通知类」消息，催设备拉取/处理 MDM 升级。
     建议新建独立 MQTT type（如 MDM_UPDATE / MDM_UPGRADE_NOTIFY），
     不要复用 STRATEGY_PULL——语义不同，端侧处理链路也应独立，避免与策略拉取混淆。
  3. 待决问题 A — 离线设备收不到推送：
     - MQTT 仅覆盖在线设备；离线/弱网可能漏收。
     - 补救：设备主动拉取策略时（如 GET /api/strategy/get，或现有拉预期快照入口）
       一并下发「待升级 MDM」标记 / 最新版本信息，使离线设备上线后仍能获知升级意图。
     - 亦可与现有 GET /api/mdm/getInfo 配合：端侧定期或策略拉取后主动查最新版本并比对本地。
  4. 待决问题 B — 自动更新 vs 仅提醒（需产品/端侧定稿）：
     - 方案一「仅提醒」：MQTT / 拉取结果只告知有新版本，由端侧弹窗或通知用户，用户确认后再升级。
     - 方案二「自动更新」：端收到通知后自行下载安装；须明确时机（立即 / 空闲 / 下次开机 / 管理员指定窗口），
       并处理 MDM 自更新风险——升级可能中断正在进行的管控会话或本地缓存，
       需约定：更新前是否强制提示用户保存工作、是否需退出敏感流程、失败回滚策略等，避免数据丢失。
     - 建议默认先做「提醒 + 用户确认」，自动静默升级作为后续可配置能力，并单独评审时机与安全边界。
