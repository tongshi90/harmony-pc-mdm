# Harmony PC MDM · 测试业务规则说明

> 面向测试人员：说明各业务模块关系、后台已落地规则与关键判定逻辑，便于设计用例与编写测试报告。  
> 本地环境：`http://localhost:8080` · Swagger：`http://localhost:8080/docs`  
> 默认管理员：`admin` / `12345678`  
> 文档基于当前代码实现整理（以仓库代码为准；若与口头约定冲突，以代码为准）。

## 1. 系统全景与两条链路

平台分两套接口前缀，权限与用途完全不同：

| 前缀 | 使用方 | 鉴权 | 操作日志 |
|------|--------|------|----------|
| `/platform/*` | 云侧管理台（浏览器） | 需登录 JWT；按菜单前缀鉴权 | 写操作默认记日志 |
| `/api/*` | 设备 MDM 客户端 | **不鉴权**（白名单） | **不记**操作日志 |

另外：`GET /platform/app/{appId}/versions/{versionId}/package` 为设备下载 HAP 专用，**免登录**（见 §3）。

### 1.1 核心业务关系（一句话）

```
成员分组 ──绑定──► 人员 ──绑定──► 设备(SN)
                │
                └── 初始策略模板（分组可指定；未指定用全局默认）【绑定后套用流程预留】

应用仓库(上架应用 + 已发布版本 + HAP)
        │
        ├── 策略下发 / 批量安装卸载 ──写入──► 预期策略快照(按 SN)
        │                              └──► 策略变更日志三表
        │
        └── 设备上报当前快照 / 已安装应用 ──► 与预期对比 → 匹配/不匹配 → 可补发 MQTT
```

### 1.2 设备策略闭环（测试必懂）

1. 云侧改「预期」：策略下发、应用批量安装/卸载、设备绑定套用初始策略 → 写 `t_device_policy_expected`，并尽量 MQTT 通知设备 `STRATEGY_PULL`。
2. **顺序约束**：必须先将本次涉及的全部预期快照 **commit 成功**，再发 `STRATEGY_PULL`；禁止先通知后落库。实现上：整批写入各设备预期 → **一次 commit** → 有界线程池并行 MQTT。策略下发 / 应用批量装卸载为「校验建任务后立即返回，后台执行落库+通知」；绑定仍同步（单设备：commit 后再 MQTT）。
3. 设备拉配置：`GET /api/strategy/get` → 拿最新任务紧急度 + 全量预期快照。
4. 设备执行后上报：当前策略进 `t_device_policy_current`；已装应用进 `t_device_app_installed`。
5. 云侧判定对齐：一般策略比「预期表 vs 当前表」；应用安装管理比「预期表 vs 已安装应用表」（见 §7）。

**重要**：策略是否「下发成功」**不以**任务表状态机为准，而以**快照是否匹配**为准。

## 2. 组织 / 人员 / 设备

### 2.1 成员分组（`t_sys_department`）

- `parent_id` 为空 = 顶级分组；选中某分组下发时，**含子组**设备（递归）。
- 分组可绑定 `initial_policy_id`（初始策略模板）；为空则使用全局「默认」模板。
- 分组删除等规则以成员分组接口校验为准（有成员/子组时不可随意删）。

### 2.2 人员（`t_sys_member`）

- 核心字段：姓名、工号、账号、密码（bcrypt）、所属分组。
- **一人一设备**：人员管理侧按「是否已有绑定设备」展示；设备绑定接口也会校验成员未绑定其它设备。
- 管理台录入成员密码走 **RSA 加密传输**；设备端绑定接口按协议传 **明文密码**（见 §8.4）。

### 2.3 设备（`t_device`）

| 字段 | 含义 | 常见值 |
|------|------|--------|
| `sn` | 设备唯一编号 | 与 MQTT client_id、接口 SN 一致 |
| `member_id` | 绑定成员 | 空 = 未绑定人员 |
| `bind_status` | 绑定/激活标记 | `0` 待激活/未绑定；`1` 已绑定激活 |
| `status` | 在线状态 | `1` 在线；`2` 离线；`3` 已挂失 |

- 机构归属：**不直接存部门**，经 `member_id → department_id` 关联。
- 在线状态由定时任务查 EMQX Clients 同步（不是 `/api/strategy/get` 更新）。

### 2.4 设备绑定规则（`POST /api/device/bind`）

全部满足才绑定成功：

1. SN 存在；
2. 设备未绑定：`member_id` 为空 **且** `bind_status ≠ 1`；
3. 账号存在、未删除、启用中，密码 bcrypt 校验通过；
4. 该成员未绑定过其它设备。

成功后（**同一事务内先写策略再返回**）：

- 写 `device.member_id`、`bind_status=1`，必要时写 `activate_time`；
- 解析初始策略模板：分组 `initial_policy_id` → 否则全局 `is_default=1`；
- 写 `t_policy_task`（`op_type=initial_bind`，紧急）+ `t_policy_task_item` + `t_policy_device_task`；
- 将模板各项写入该 SN 的 `t_device_policy_expected`；
- 返回 `name`（成员姓名）、`groupName`（所属分组名称）；
- 尽力发 MQTT `STRATEGY_PULL`（失败不影响已绑定）。

因此设备绑定成功后立刻调 `/api/strategy/get`，应能拉到初始策略 snapshot。

失败示例（接口 `message`）：设备不存在 / 设备已被绑定 / 账号或密码错误 / 账号已禁用 / 该成员已绑定其它设备。

## 3. 鉴权、菜单与白名单

### 3.1 管理台登录

- 内置 `admin`：超级管理员，天然全菜单，不出现在管理员列表

### 3.2 菜单与接口前缀（无菜单权限则 401）

## 4. 应用管理

### 4.1 应用与版本状态

**应用（`t_app_base`）**

| status | 含义 |
|--------|------|
| 1 | 上架 |
| 0 | 下架 |

**版本（`t_app_version`）**

| status | 含义 |
|--------|------|
| 0 | 草稿 |
| 1 | 待测试 |
| 2 | **已发布** |
| 3 | 已下架 |

- 协议字段：`app_id` = 端侧 AppIdentifier；`bundle_name` = 包名。  
  **注意**：设备接口返回的 `appId` 是业务字段 `app_id`，**不是**表主键雪花 ID。  
  下载 URL 路径里的数字才是主键 ID。

### 4.2 安装包与下载地址

- 上传后本地落盘，下载 URL 形态：  
  `{origin}/platform/app/{应用主键}/versions/{版本主键}/package`
- 该 GET 已白名单，设备可无 Token 下载。
- 无 `file_path`（未上传 hap）时：`has_package=false`，下载地址为空。

### 4.3 设备应用市场列表（`GET /api/app/list`）

返回条件：

1. 应用 **上架**（`status=1`）；
2. 具备有效 `app_id`、`bundle_name`；
3. 至少有一个 **已发布** 版本；
4. 版本取已发布中 **版本号最高**（先比 `version_code`，再比 `version_name`）；
5. `bundleDownloadUrl` 用该版本；未上传包则为空字符串。

返回字段：`appId` / `appName` / `appDesc` / `bundleName` / `version` / `bundleDownloadUrl`。

### 4.4 批量安装 / 批量卸载（应用详情 · 安装情况）

入口：应用详情 →「安装情况」Tab。

| 操作 | 前端必填 | 后端 `op_type` | 策略紧急度 |
|------|----------|----------------|------------|
| 批量安装 | 分组（可全选再取消部分）、已发布且有包的版本 | `app_batch` | **固定普通 + 最多等待 24 小时** |
| 批量卸载 | 仅分组 | `app_batch` | 同上 |

共同效果：

1. 写策略变更日志三表（见 §5）；
2. 同步创建任务后返回；后台按规则合并每台设备的 `APP_MANAGEMENT` **预期快照**（见 §6.2），整批 **commit** 后再并行 MQTT；
3. 有实际变更且在线的设备发 `STRATEGY_PULL`；无变更（skipped）不发。

分组范围：与策略下发一致，勾选分组 **含子组** 下人员绑定的设备。

## 5. 策略变更日志三表（统一模型）

凡「改了设备预期策略」的操作，共用：

| 表 | 作用 |
|----|------|
| `t_policy_task` | 变更单头：名称、来源类型、紧急度、截止时间、目标描述等 |
| `t_policy_task_item` | 本次配置的策略项快照（`policy_code` + `param_json`） |
| `t_policy_device_task` | 本次影响到的设备/人员清单（**不做执行状态机**） |

### 5.1 `op_type`（变更来源）

| 值 | 含义 | 紧急度规则 |
|----|------|------------|
| `dispatch` | 管理台「策略下发」创建 | **前端选择**：普通 / 紧急；普通可选等待小时（1/2/4/8/12/24） |
| `app_batch` | 应用批量安装/卸载 | **固定** `normal`，等待 **24** 小时，写 `deadline_at` |
| `initial_bind` | 设备绑定后套用初始策略 | **固定** `urgent`（立即执行）；见 §2.4 / §8.4 |

策略下发列表默认只查 `op_type=dispatch`。

### 5.2 普通 vs 紧急

| 类型 | `policy_level` | `wait_hours` / `latestExecutionTime` |
|------|----------------|--------------------------------------|
| 普通 | `normal` | 有等待小时与截止时间 |
| 紧急 | `urgent` | 无等待、无截止（立即执行语义） |

设备拉取时（`/api/strategy/get`）返回的 `policyLevel` / `latestExecutionTime` 取该 SN **最新一条**关联任务（见 §8.1）。

## 6. 策略配置与预期快照

### 6.1 策略下发（管理台）

1. 选择目标：按分组（含子组）或手动选人（仅已绑设备成员）。
2. 配置一条或多条策略项（同 Code 后者覆盖前者）。
3. 选择普通/紧急及等待时间。
4. 后端：同步校验并写任务头 + 策略项 + 目标设备明细后立即返回；后台整批 **覆盖写入**预期快照并 **一次 commit**，再并行 MQTT `STRATEGY_PULL`（见上文顺序约束）。任务 `ext.apply_status`：`pending` → `applying` → `done` / `failed`。

`PASSWORD_POLICY` 提交时会规范为协议 Code `PSW_MANAGEMENT`。

密码策略 `validityPeriod`：管理台 / 初始策略 / 下发任务按**天**配置与落库；写入 `t_device_policy_expected` 时换算为**毫秒**（`天 × 86400000`），`GET /api/strategy/get` 返回的亦为毫秒。

### 6.1.1 `APP_CONFIG_MANAGEMENT` 参数格式

三份名单均为对象数组（含应用名，便于设备侧展示）：

```json
{
  "sceneCode": "APP_CONFIG_MANAGEMENT",
  "param": {
    "allowAppIds": [{"appId": "0001", "appName": "企业邮箱"}],
    "disallowAppIds": [{"appId": "0001", "appName": "企业邮箱"}],
    "disallowedUninstallAppIds": [{"appId": "0001", "appName": "企业邮箱"}]
  }
}
```

兼容历史纯字符串 `appId` 列表：写入预期快照 / 设备拉取时会补齐为 `{appId, appName}`。合规对比仅按 `appId`，忽略 `appName` 文案差异。

### 6.2 `APP_MANAGEMENT` 参数格式（已调整）

**不再包含** `totalApps`。标准形态：

```json
{
  "currentApps": [
    {
      "appId": "业务AppId",
      "bundleName": "com.xxx",
      "version": "版本名 version_name",
      "bundleDownloadUrl": "https://host/platform/app/.../package"
    }
  ],
  "uninstallApps": ["com.xxx.to.uninstall"]
}
```

- `currentApps`：需安装/更新列表；
- `uninstallApps`：需卸载的 **bundleName** 字符串列表。

### 6.3 批量安装合并预期的规则（按设备）

对每台设备读已有 `APP_MANAGEMENT` 预期，再合并：

**安装**

| 情况 | 处理 |
|------|------|
| 名单中已有该应用，且版本 **≥** 本次 | **忽略**（skipped），不改快照、不 MQTT |
| 已有但版本 **<** 本次 | **更新**版本与下载地址 |
| 名单中没有 | **新增**一条需安装 |

同时会从该设备的 `uninstallApps` 中去掉同 bundle（避免装又卸冲突）。

**卸载**

| 情况 | 处理 |
|------|------|
| 已在卸载名单 | skipped |
| 否则 | 追加到 `uninstallApps`，并从 `currentApps` 去掉同 bundle |

### 6.4 策略下发覆盖 vs 批量合并

- **策略下发**含 `APP_MANAGEMENT`：对该 Code **整包覆盖**预期 param。
- **应用批量**：在原有预期上 **按条合并**，不会无故清空其它应用项。

测试时注意：同一设备先下发全量应用列表，再批量装另一应用，结果应是合并后的名单，而不是只剩批量那一个。

### 6.5 Wifi 客户端证书

`WIFI_SET.certEntry`：前端读文件为 DataURL 后去掉前缀，入库为 **纯 Base64 字符串**。  
快照对比时 **忽略** `certEntry` 字段差异（见 §7）。

### 6.6 远程操控（`REMOTE_CONTROL`）

`operationType` 仅保留：

| Code | 文案 |
|------|------|
| `lockDevice` | 设备锁定 |
| `unlockDevice` | 设备解除锁定 |

参与预期 vs 当前表对比（已纳入匹配判定）。

## 7. 快照匹配判定（测试报告核心）

入口逻辑：`device_snapshot_service.get_device_snapshot_compare`。  
管理台「终端策略对齐」、设备合规展示、上线补发 MQTT 都依赖 `consistent`（`true`=匹配）。

### 7.1 一般策略（表对表）

对比：

- 预期：`t_device_policy_expected`
- 当前：`t_device_policy_current`

按 `policy_code`：

| 情况 | 结果 |
|------|------|
| 预期有、当前无 | 不匹配（`missing_current`） |
| 当前有、预期无 | 不匹配（`missing_expected`） |
| 两边都有，param 规范化后相等 | 该条通过 |
| param 不等 | 不匹配（`param_mismatch`） |

规范化要点：忽略字段顺序；列表会排序后再比。

**字段忽略**：仅 `WIFI_SET` 忽略 `certEntry`（证书内容不同不算不匹配）。

**REMOTE_CONTROL**：按上表正常对比（不再排除）。

### 7.2 `APP_MANAGEMENT`（特殊：预期 vs 已安装应用）

**不**与 `t_device_policy_current` 比，而与 `t_device_app_installed`（关联应用/版本）比。

**需安装（`currentApps`）**

- 按 `appId` 或 `bundleName` 在安装表找应用；
- 必须找到，且安装版本的 `version_name` **≥** 预期里的 `version`；
- 未安装或版本更低 → 不匹配。

**需卸载（`uninstallApps`）**

- 若安装表仍存在该 `bundleName` → 不匹配；
- 不存在 → 该条通过。

全部安装/卸载要求都满足 → `APP_MANAGEMENT` 视为对齐。

### 7.3 匹配结论

任一策略存在 diff ⇒ `consistent=false`（不匹配）；全部通过 ⇒ 匹配。

上线补发：仅对 **不匹配** 且在线的设备补发 `STRATEGY_PULL`。

## 8. 设备侧接口一览（`/api/*`）

统一响应：

```json
{ "code": 0, "message": "", "data": {} }
```

`code=0` 成功且 `message` 通常为空；失败时 `message` 为原因（HTTP 状态码可能为 400/404 等）。

### 8.1 拉取策略 · `GET /api/strategy/get`

参数：`sn` 或 `SN`（必填其一）。

逻辑：

1. 经 `t_policy_device_task` 找该 SN 关联的 **最新** `t_policy_task`（按创建时间倒序）；
2. 取 `policyLevel`；若为 `normal` 则带 `latestExecutionTime`（截止时间）；紧急则为 `null`；
3. 无历史任务时两者可为 `null`；
4. `snapshot` = 该 SN **全部**预期策略（协议形态：`sceneCode`/`commandCode` + `param`；Wifi 用 `commandCode`）。

**不会**在此接口更新在线状态。

### 8.2 位置上报 · `POST /api/report/location`

Body：`SN`、`longitude`、`latitude`（字符串，须能解析为数字）。

- SN 须存在；
- 追加写入 `t_device_location_log`（轨迹日志，不去重）；
- 成功 `data` 为空对象。

### 8.3 应用列表 · `GET /api/app/list`

见 §4.3。Param 可空。

### 8.4 设备绑定 · `POST /api/device/bind`

见 §2.4。Body：`SN`、`userName`、`password`（明文）。

### 8.5 其它协议接口

协议文档中还有快照上报、应用详情、MDM 版本等；**未在本文展开的表示尚未完全按协议落地或仍为占位**，测前请对照 Swagger / 代码确认。

## 9. MQTT 与在线

| 能力 | 说明 |
|------|------|
| 业务 MQTT | 配置在平台「MQTT」；向 `mdm/{SN}/...` 发通知 |
| 策略拉取通知载荷 | `{"type":"STRATEGY_PULL"}` |
| 在线同步 | 定时用 EMQX Dashboard 账号调 Clients API；SN 作为 client_id |
| 下发/批量前 | 先尝试同步在线；失败则降级对目标尽量全量发通知 |
| 离线设备 | 本次可能跳过通知；上线后若快照仍不匹配会补发 |

测试「是否收到拉取通知」时，需区分：任务已创建、预期已改，与 MQTT 是否发出是两件事。

## 10. 操作日志（管理台）

- 默认记录：`POST/PUT/PATCH/DELETE`（成功失败都记）；
- 普通 `GET` 不记；导出等只读但要记的接口会加审计注解；
- `/api/*`、健康检查、公钥、`/me`、带 `@no_audit` 的不记；
- 密码等敏感字段入库脱敏为 `******`；
- `admin` 可看全部日志，其它账号仅本人。

## 11. 建议测试场景清单（按模块）

### 11.1 绑定

- [ ] 未登记 SN → 失败  
- [ ] 已绑定设备再绑 → 失败  
- [ ] 错误密码 → 失败  
- [ ] 成员已绑其它设备 → 失败  
- [ ] 正常绑定 → 返回姓名/部门，设备 `bind_status=1`  
- [ ] 禁用成员 → 失败  

### 11.2 应用与批量

- [ ] 仅上架、无已发布版本 → 批量安装不可用  
- [ ] 已发布但无 hap → 不可选或提交失败  
- [ ] 批量安装写 `op_type=app_batch`，普通 + 24h 截止  
- [ ] 同设备同应用更高版本已在预期 → skipped，预期不变  
- [ ] 更低版本 → 预期版本与下载地址更新  
- [ ] 批量卸载后预期 `uninstallApps` 含 bundle，且从安装名单移除  
- [ ] `/api/app/list` 只含上架，版本为最高已发布，`appId` 为业务字段  

### 11.3 策略下发与拉取

- [ ] 分组含子组设备都进 `t_policy_device_task`  
- [ ] 紧急任务无 `deadline`；普通有  
- [ ] `/api/strategy/get` 返回最新任务紧急度 + 全量预期 snapshot  
- [ ] HAP URL 无 Token 可下载；上传仍需登录  

### 11.4 快照匹配

- [ ] 一般策略：改预期未上报 → 不匹配；上报一致 → 匹配  
- [ ] Wifi 仅证书不同 → 仍匹配  
- [ ] `REMOTE_CONTROL` 预期与当前不一致 → 不匹配  
- [ ] `APP_MANAGEMENT`：未装/低版本 → 不匹配；版本达标 → 匹配  
- [ ] 预期卸载但安装表仍有 → 不匹配  
- [ ] 不匹配设备上线后应能补发拉取通知（环境需 MQTT 可用）  

### 11.5 位置

- [ ] 合法经纬度追加日志  
- [ ] 非法坐标 / 不存在 SN → 失败

## 13. 已知预留 / 未完成（避免误测）

- **初始策略绑定**（`initial_bind`）：`POST /api/device/bind` 成功落库时已接通——按成员所属分组的初始策略（未指定则用全局默认）写入三表日志 + 预期快照（紧急策略），再返回绑定成功，保证随后 `/api/strategy/get` 可拉到。  
- 协议中部分上报/详情接口可能仍为占位。  
- 数据看板等页面可能仍含 Demo 静态数据。  
- 登录调试期若关闭了管理员密码校验，以当前 `auth_service` 为准（上线前应恢复）。
